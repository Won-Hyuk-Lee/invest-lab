# invest-lab 앞으로 할 일 — 조사 결과와 확정 방향

작성: 2026-09-25. 조사·논의를 거쳐 **초기 운용 방식과 중심 전략을 확정**했다. 아래 기능 목록은 후속 개발 계획이며 계산 임계값·주문 한도는 실험 후보로 남긴다. 이번 작업은 코드 확인·공식 자료 조사·문서 작성이며, 키 읽기·한투 계좌 조회·주문 전송은 수행하지 않았다.

## 사용자와 확정한 방향

1. **일봉으로 전체 분석 + 후보 10~20개 장중 감시.** 분석 대상은 코스피 주식과 국내 상장 ETF이며, 국내 상장 미국 지수 ETF를 포함한다. 기존에 합의한 거래일 기준을 유지한다.
2. **코스피 상승 추세의 눌림목을 중심 전략으로 검증하고 ETF 추세와 비교.** 평균회귀·가치/품질·매크로는 확장 연구 목록에 유지한다.

운용의 기본 흐름은 확정 일봉 수집·분석 → 후보 선정 → 다음 거래일 주문 조건 확인 → 장중 감시 → 체결·잔고 대조로 정리한다. 장중 감시는 가격·호가·주문 상태를 관찰하는 기능이며, 감시 여부만으로 장중 자동 청산 규칙까지 확정된 것은 아니다.

눌림목 판단에 사용할 ATR 배수·RSI 범위, 매도 조건, 보유 기간, 위험 예산과 주문 금액은 백테스트의 실험 설정으로 명시한다. 첫 전략 선택을 임계값의 검증 완료나 실전 주문 활성화로 해석하지 않는다.

다음 개발 묶음은 **한투 실제 시세·모의계좌 보유 조회와 일봉 저장**이다. 그 뒤 수동 모의주문/체결 대조 → 중심 전략 계산과 과거 검증 → 제한된 자동 모의운용 순서로 진행한다.

## 현재 상태와 다음 목표

현재 코드를 확인한 결과, React 화면·Python 계산·SQLite 로컬 계좌·전략 버전 관리는 존재한다. 시세 공급자는 `DemoMarket`이며 한투 어댑터, 실제 보유 조회, 외부 주문, 백테스트, 배치 수집은 없다. 현재 점수는 검증 전 기술적 가중합이다.

다음 목표는 **실제 시세 → 신뢰할 수 있는 지표 → 설명 가능한 전략 → 한투 모의계좌의 주문/체결 → 과거 검증과 운용 기록**을 연결하는 것이다. 실전 투자 기능은 후속 단계의 별도 운용 모드로 설계한다.

현재의 `local_simulation`, 앞으로의 `kis_paper`, `kis_live`를 화면·저장소·환경 설정·주문 기록에서 구분한다. 오류가 나도 모의 환경이 실전으로 자동 전환되면 안 된다.

## 구현 순서 제안

### 1. 실제 시세와 모의계좌를 읽는 단계

K01~K03, K06, D01~D03, U01부터. 화면의 샘플 데이터를 실제 값으로 교체하는 것과 내 계좌 연동을 각각 완료한다. 값이 없거나 통신에 실패하면 샘플로 조용히 대체하지 않는다. 같은 화면에서 두 데이터가 섞이지 않게 한다.

### 2. 수동 모의주문과 데이터 품질을 검증하는 단계

K04~K05, D04~D05, O02~O03. 매수뿐 아니라 매도·취소·부분 체결과 오류 복구까지 처리한다. HTTP 성공은 접수 결과이며, 체결을 확인하기 전 보유 수량에 임의로 더하지 않는다. 로컬 DB의 request_id만으로 증권사 중복 주문이 예방된다고 간주하지 않는다.

### 3. 전략 연구와 과거 검증 단계

I01~I02, S01~S02, B01~B03, R01. 코스피 눌림목을 중심으로 계산과 과거 검증을 구성하고 ETF 추세를 비교 전략으로 둔다. 평균회귀는 후속 실험이다. 장기 하락 종목에 RSI만 낮다고 높은 매수 점수를 주는 현재 초기 모델을 그대로 자동 주문에 연결하지 않는다.

### 4. 제한된 자동 모의운용 단계

O01, R02, U02를 추가한다. 샘플 장부, 과거 검증, 한투 모의계좌가 같은 전략 규칙을 사용하게 하되 체결 어댑터는 다르게 둔다. 한 달은 시스템 안정성과 가설의 초기 관찰 기간으로 삼고, 짧은 승률만으로 실전 전환하지 않는다.

### 5. 데이터가 갖춰진 확장 단계

ETF 특화, 가치·품질, 매크로, 통계 모델을 한 번에 섞지 않고 별도 실험으로 추가한다. 인프라는 이때 운영 필요에 맞춰 결정한다. 실전 계좌 연결과 주문 활성화는 사용자가 범위와 한도를 확정한 뒤 진행한다.

## 헥사고날 구조의 다음 경계

현재 `PortfolioRepository.buy()`는 로컬 장부를 위해 설계됐다. 여기에 외부 주문을 그대로 끼워 넣으면 접수와 체결을 혼동할 수 있으므로 다음 역할을 분리한다.

```text
MarketData / BarRepository     시세 수신과 검증된 과거 데이터
Broker                        계좌 조회, 주문 접수, 상태 조회, 정정/취소
OrderRepository               주문 의도·외부 주문번호·상태·체결 이벤트
Strategy / RiskPolicy         신호, 청산, 수량, 한도 계산
Portfolio                     브로커 체결을 반영한 보유·현금 상태
Clock / TradingCalendar       시간과 거래 가능 세션
JobRunner                     수집·계산·대조 작업 실행
```

API 화면 요청, 배치 작업, 백테스트가 도메인 계산을 공유한다. 초기 로컬은 단일 작업자와 기존 SQLite로 충분한지 먼저 측정한다. 대용량 일봉/연구 쿼리에서 필요하면 파일형 시계열 저장과 분석 엔진을 별도 어댑터로 추가한다. 처음부터 분산 작업 시스템을 도입할 필요는 없다.

계산 함수는 데이터만 받으며 HTTP나 DB를 호출하지 않는다. 외부 API 지연이 계산 속도를 제한하지 않게 캐시/저장 이후 계산한다. 연구 화면을 여러 번 열어도 같은 종목 일봉을 매번 한투에서 가져오지 않는다.

## 선택 근거와 남은 실험 설정

### 운용 방식별 차이

아래 비교를 거쳐 사용자는 첫 번째 방식인 일봉 분석 + 후보 장중 감시를 선택했다. 다른 방식은 향후 변경 검토를 위해 남긴다.

| 방식 | 신호 계산 | 장중 동작 | 추가 구현 부담 |
| --- | --- | --- | --- |
| 일봉 분석 + 후보 감시 | 확정 일봉으로 하루 한 번 후보와 진입 조건 계산 | 보유/후보의 가격·체결·주문 상태 감시. 일봉 지표를 매 틱마다 재계산하지 않음 | 실시간 재접속, 오래된 시세 감지, 감시 대상 구독 관리 |
| 하루 한 번만 운용 | 확정 일봉 분석 후 다음 세션 주문 목록 작성 | 정해진 주문·잔고 대조 시간에만 실행 | 가장 단순. 장중 가격 손절을 실행하는 모델로 설명하면 안 됨 |
| 소수 종목 장중 전략 | 사전 선택한 분봉 주기로 신호 재계산 | 진입·청산 판단과 체결 감시 반복 | 분봉 이력, 미완성 봉 처리, 틱/분봉 정합성, 비용·미체결 검증 추가 |

확정한 방식에서는 일봉 신호와 장중 감시를 분리한다. 초기 세션 범위는 KRX 정규장을 제안하며, 주문 조건 확인 시점과 장중 청산 여부는 전략 설정에 기록하고 백테스트에도 같은 관측 주기를 적용한다.

로컬 PC가 꺼져 있으면 앱의 감시와 주문 로직도 멈춘다. 따라서 ‘앱에서 계산한 손절선’과 ‘증권사에 이미 접수되어 유효한 주문’을 화면에서 구분해야 한다. 재시작 시 지난 신호를 일괄 주문하지 않고 현재 미체결·체결·보유를 먼저 조회한다.

### 첫 전략 선택에 따른 구현 순서

| 중심 전략 | 공통 조회 연동 이후 먼저 할 일 | 비교 기준 |
| --- | --- | --- |
| 코스피 눌림목 | ATR·이격도·RSI·추세 필터, 진입/청산/수량 정의 | 같은 대상의 단순 보유와 시장 지수. ETF 추세는 별도 전략 실험으로 비교 |
| ETF 추세 | 일봉·이평 기울기·분배금/환헤지 메타데이터, 리밸런싱 규칙 | 같은 ETF의 단순 보유, 같은 현금·비용 가정 |
| 코스피 평균회귀 | z-score·ADX·유동성, 강한 하락 제외와 짧은 보유 규칙 | 같은 대상·기간의 눌림목 전략과 비교 |

코스피와 ETF 전략의 수익률만 나란히 두고 우열을 확정하지 않는다. 투자 대상·시장 노출·현금 비중·위험 예산 차이를 보고하고 각 전략에 맞는 벤치마크와 먼저 비교한다. 사용자가 선택한 코스피 눌림목 중심·ETF 추세 비교를 우선하며, 다른 연구 항목은 목록에 유지한다.
